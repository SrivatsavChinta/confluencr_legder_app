## Overview

The API manages accounts, records credits and debits against them as ledger entries, reports balances and transaction history, and transfers money between accounts atomically.

| Item | Value |
| ---- | ----- |
| Local base URL | `http://127.0.0.1:8000` |
| Swagger UI | <http://127.0.0.1:8000/docs> |
| ReDoc | <http://127.0.0.1:8000/redoc> |
| OpenAPI schema | <http://127.0.0.1:8000/openapi.json> |
| Authentication | None. All endpoints are public; authentication and authorization are outside the scope of the assessment. |

The interactive documentation is generated from the same code and lists every endpoint below with its request schema, response schema, and documented `404` / `409` responses.

## General Conventions

### Requests and responses

- Request bodies are JSON and must be sent with `Content-Type: application/json`.
- Responses are JSON.
- Request bodies reject unknown fields. Sending a field that is not listed for an endpoint (for example `balance` when creating an account) returns `422`.
- String fields in request bodies (`name`, `reference_id`, `description`) must be JSON strings and have leading and trailing whitespace removed before validation and storage.
- IDs are positive integers generated by the database.

### Money

All amounts are Indian rupees (INR).

| Direction | Format |
| --------- | ------ |
| Requests | A JSON **string** containing a decimal number, for example `"500.00"`, `"500.5"`, or `"500"`. JSON numbers (`500`, `500.0`) and booleans are rejected with `422`. |
| Responses | A JSON string with exactly two decimal places, for example `"0.00"` or `"1234.50"`. |

Request amounts must:

- be greater than `0`,
- have at most two decimal places (`"10.001"` is rejected, not rounded; trailing zeros such as `"500.000"` are accepted because the value is exactly `500.00`),
- be finite (`"NaN"` and `"Infinity"` are rejected),
- be at most `"92233720368547758.07"`, the largest amount that fits in the database as whole paise.

Surrounding whitespace and exponent notation (for example `"1e2"`, meaning `100.00`) are accepted by the decimal parser.

### Timestamps

Timestamps are generated by the server in UTC and returned in ISO 8601 format with a `Z` suffix, for example `"2026-10-27T12:00:00.123456Z"`. Fractional seconds are included when non-zero.

### Error responses

Every error response is a JSON object with a `detail` field:

| Status | `detail` format | Example |
| ------ | --------------- | ------- |
| `404`, `409`, `500` | A message string | `{"detail": "Account not found"}` |
| `422` | FastAPI's list of validation errors. Each item has `type`, `loc` (where the error is, such as `["body", "amount"]` or `["query", "limit"]`), `msg`, and `input`; some include `ctx`. | See below |

Example `422` response for `{"name": "   "}`:

```json
{
  "detail": [
    {
      "type": "string_too_short",
      "loc": ["body", "name"],
      "msg": "String should have at least 1 character",
      "input": "   ",
      "ctx": {"min_length": 1}
    }
  ]
}
```

### Validation order

Path parameters, query parameters, and the request body are validated before the endpoint runs. A request with invalid input therefore returns `422` even if the account it refers to does not exist. Business rules (account existence, duplicate references, sufficient balance) are checked only for valid requests.

## Accounts

### `POST /api/accounts`

Creates an account.

The server generates `id` and `created_at`, and every new account starts with a balance of `0.00`. The client cannot set the balance: only `name` is accepted, and any other field returns `422`.

**Request body**

| Field | Type | Required | Rules |
| ----- | ---- | -------- | ----- |
| `name` | string | Yes | Trimmed; 1–100 characters after trimming. Longer names are rejected, not truncated. Names do not have to be unique. |

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/api/accounts \
  -H "Content-Type: application/json" \
  -d '{"name": "Alice"}'
```

**Response `201 Created`**

```json
{
  "id": 1,
  "name": "Alice",
  "balance": "0.00",
  "created_at": "2026-10-27T12:00:00.123456Z"
}
```

| Status | When |
| ------ | ---- |
| `201` | Account created |
| `422` | `name` missing, not a string, blank, or longer than 100 characters; unknown field (such as `balance`); malformed JSON |
| `500` | Unexpected database error |

**Example error `422`** (client tried to set the balance)

```json
{
  "detail": [
    {
      "type": "extra_forbidden",
      "loc": ["body", "balance"],
      "msg": "Extra inputs are not permitted",
      "input": "100.00"
    }
  ]
}
```

### `GET /api/accounts`

Lists every account, newest first (by `created_at`, then by `id` for accounts created at the same instant). This list is not paginated.

**Response `200 OK`**

| `200` | Success |
| `500` | Unexpected database error |

## Credit and Debit Transactions

### `POST /api/accounts/{account_id}/transactions`

Records a credit or debit against an account and updates its balance.

- A **credit** increases the balance by `amount`.
- A **debit** decreases the balance by `amount`. If the balance is less than `amount`, the debit is rejected with `409` and nothing changes.

**Request body**

| Field | Type | Required | Rules |
| ----- | ---- | -------- | ----- |
| `type` | string | Yes | Exactly `"credit"` or `"debit"` (lowercase) |
| `amount` | string | Yes | Decimal string; see [Money](#money) |
| `reference_id` | string | Yes | Trimmed; 1–100 characters after trimming; unique per account (case-sensitive) |
| `description` | string or `null` | No | Trimmed; at most 255 characters. Omitted, `null`, or blank is stored as `null`. |

The client cannot set `id`, `account_id` (taken from the path), `created_at`, or `balance_after`.

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/api/accounts/1/transactions \
  -H "Content-Type: application/json" \
  -d '{"type": "credit", "amount": "1000.00", "reference_id": "DEP-001", "description": "Salary"}'
```

**Response `201 Created`**

```json
{
  "id": 1,
  "account_id": 1,
  "type": "credit",
  "amount": "1000.00",
  "description": "Salary",
  "reference_id": "DEP-001",
  "created_at": "2026-10-27T12:01:00Z",
  "balance_after": "1000.00"
}
```

`balance_after` is the account balance immediately after this transaction. It is returned in this response only; it is not stored and does not appear in the transaction history.

**Status codes**

| Status | When | Body |
| ------ | ---- | ---- |
| `201` | Transaction recorded | Transaction with `balance_after` |
| `404` | Account does not exist | `{"detail": "Account not found"}` |
| `409` | `reference_id` already used on this account | `{"detail": "A transaction with this reference_id already exists for this account"}` |
| `409` | Debit larger than the current balance | `{"detail": "Insufficient balance"}` |
| `409` | Credit would push the balance above `92233720368547758.07` | `{"detail": "Resulting balance would exceed the maximum supported amount"}` |
| `422` | Invalid `account_id`, missing or invalid field, unknown field, or malformed JSON | Validation error list |
| `500` | Unexpected database error | `{"detail": "Internal server error"}` |

**Example error `422`** (JSON number instead of a decimal string)

```json
{
  "detail": [
    {
      "type": "value_error",
      "loc": ["body", "amount"],
      "msg": "Value error, amount must be a decimal string, for example \"500.00\"",
      "input": 500,
      "ctx": {"error": {}}
    }
  ]
}
```

### Reference ID uniqueness and duplicate requests

- A `reference_id` can be used only once per account. It is compared after trimming and is case-sensitive (`TXN-1` and `txn-1` are different).
- The same `reference_id` may be used on different accounts.
- Resubmitting a request with a `reference_id` already used on the account returns `409` with the duplicate message. No new transaction is created and the balance does not change. The original transaction is **not** returned.
- If a request is both a duplicate and an overdraft, the duplicate error is returned.
- A request rejected for another reason (for example `409 Insufficient balance` or `422`) stores nothing, so its `reference_id` remains available.
- Uniqueness is enforced by the database constraint `UNIQUE (account_id, reference_id)`, so simultaneous duplicate requests produce exactly one transaction.

Transfers also create transactions; their reference IDs share this per-account namespace (see [Reference ID behavior](#reference-id-behavior)).

### Atomicity

Each request runs in a single database transaction:

1. Check the account exists (`404` otherwise).
2. Insert the ledger entry. A reused `reference_id` fails here on the unique constraint, before the balance is touched.
3. Update the balance with a single conditional statement, for example for a debit: `UPDATE accounts SET balance = balance - :amount WHERE id = :id AND balance >= :amount RETURNING balance`. If no row matches, the request is rejected with `409`.
4. Commit.

If any step fails, the entry and the balance change are both rolled back. Because the balance check and the change are one SQL statement, concurrent debits cannot overdraw an account.

## Transaction History

### `GET /api/accounts/{account_id}/transactions`

Returns an account's ledger entries one page at a time, newest first. Entries created by transfers appear here like any other credit or debit.

**Query parameters**

| Parameter | Type | Default | Constraints |
| --------- | ---- | ------- | ----------- |
| `type` | string | none (both types) | `credit` or `debit` (lowercase) |
| `page` | integer | `1` | `1` to `92233720368547758` |
| `limit` | integer | `10` | `1` to `100` (page size) |

**Example request**

```bash
curl "http://127.0.0.1:8000/api/accounts/1/transactions?type=debit&page=1&limit=2"
```

**Response `200 OK`**

```json
{
  "data": [
    {
      "id": 3,
      "account_id": 1,
      "type": "debit",
      "amount": "300.00",
      "description": "Rent share",
      "reference_id": "TRF-001",
      "created_at": "2026-10-27T12:03:00Z"
    },
    {
      "id": 2,
      "account_id": 1,
      "type": "debit",
      "amount": "250.00",
      "description": "Groceries",
      "reference_id": "PAY-001",
      "created_at": "2026-10-27T12:02:00Z"
    }
  ],
  "pagination": {
    "current_page": 1,
    "page_size": 2,
    "total_records": 2,
    "total_pages": 1
  }
}
```

**Behavior**

- **Filtering:** with `type`, only entries of that type are returned and counted. Without `type`, both credits and debits are returned.
- **Ordering:** newest first by `created_at`; entries with the same timestamp are ordered by `id`, highest first. The order is stable across pages.
- **Pagination metadata:** `current_page` and `page_size` echo the request; `total_records` is the number of matching entries; `total_pages` is `ceil(total_records / page_size)`.
- **No matching records:** `200` with `"data": []`, `total_records: 0`, and `total_pages: 0`. This includes an account with no transactions.
- **Page beyond the last page:** `200` with `"data": []` and the correct `total_records` and `total_pages`.
- This endpoint is read-only.

| Status | When |
| ------ | ---- |
| `200` | Success, including empty results |
| `404` | `{"detail": "Account not found"}` |
| `422` | Invalid `account_id`, `type`, `page`, or `limit` |
| `500` | Unexpected database error |

**Example error `422`** (`limit=101`)

```json
{
  "detail": [
    {
      "type": "less_than_equal",
      "loc": ["query", "limit"],
      "msg": "Input should be less than or equal to 100",
      "input": "101",
      "ctx": {"le": 100}
    }
  ]
}
```

## Money Transfers

### `POST /api/transfers`

Moves money from a source account to a destination account in one atomic operation.

**Request body**

| Field | Type | Required | Rules |
| ----- | ---- | -------- | ----- |
| `source_account_id` | integer | Yes | JSON integer `>= 1` (strings such as `"1"` and booleans are rejected); must exist |
| `destination_account_id` | integer | Yes | Same rules; must exist; must differ from `source_account_id` |
| `amount` | string | Yes | Decimal string; see [Money](#money) |
| `reference_id` | string | Yes | Trimmed; 1–100 characters; see [Reference ID behavior](#reference-id-behavior) |
| `description` | string or `null` | No | Trimmed; at most 255 characters; blank is stored as `null` |

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/api/transfers \
  -H "Content-Type: application/json" \
  -d '{"source_account_id": 1, "destination_account_id": 2, "amount": "300.00", "reference_id": "TRF-001", "description": "Rent share"}'
```

**Response `201 Created`** (account 1 had `750.00`, account 2 had `0.00`)

```json
{
  "id": 1,
  "source_account_id": 1,
  "destination_account_id": 2,
  "amount": "300.00",
  "reference_id": "TRF-001",
  "description": "Rent share",
  "created_at": "2026-10-27T12:03:00Z",
  "debit_transaction": {
    "id": 3,
    "account_id": 1,
    "type": "debit",
    "amount": "300.00",
    "description": "Rent share",
    "reference_id": "TRF-001",
    "created_at": "2026-10-27T12:03:00Z"
  },
  "credit_transaction": {
    "id": 4,
    "account_id": 2,
    "type": "credit",
    "amount": "300.00",
    "description": "Rent share",
    "reference_id": "TRF-001",
    "created_at": "2026-10-27T12:03:00Z"
  },
  "source_balance_after": "450.00"
}
```

Only the source account's resulting balance is returned. The destination's balance is available from `GET /api/accounts/{account_id}/balance` (here it would be `300.00`).

**Status codes**

| Status | When | Body |
| ------ | ---- | ---- |
| `201` | Transfer completed | Transfer with both ledger entries |
| `404` | Source account does not exist | `{"detail": "Source account not found"}` |
| `404` | Destination account does not exist | `{"detail": "Destination account not found"}` |
| `409` | `reference_id` already used on the source or destination account | `{"detail": "reference_id has already been used on the source or destination account"}` |
| `409` | Source balance is less than `amount` | `{"detail": "Insufficient balance"}` |
| `409` | Credit would push the destination above `92233720368547758.07` | `{"detail": "Destination balance would exceed the maximum supported amount"}` |
| `422` | Invalid or missing field, unknown field, malformed JSON, or source equals destination | Validation error list |
| `500` | Unexpected database error | `{"detail": "Internal server error"}` |

If both accounts are missing, the source error is returned.

**Example error `422`** (source equals destination)

```json
{
  "detail": [
    {
      "type": "value_error",
      "loc": ["body"],
      "msg": "Value error, source_account_id and destination_account_id must be different",
      "input": {"source_account_id": 1, "destination_account_id": 1, "amount": "100.00", "reference_id": "TRF-002"},
      "ctx": {"error": {}}
    }
  ]
}
```

### Ledger entries

A successful transfer creates, with one shared timestamp:

- one transfer record (source, destination, amount),
- one `debit` transaction on the source account,
- one `credit` transaction on the destination account.

Both transactions carry the transfer's `amount`, `reference_id`, and `description`, and are linked to the transfer record in the database. They appear in each account's transaction history and are filtered and paginated like any other entry. The link to the transfer (`transfer_id`) is stored in the database but is not included in transaction responses.

### Reference ID behavior

The transfer record itself has no reference column. The `reference_id` is stored on both ledger entries, which are subject to the per-account rule `UNIQUE (account_id, reference_id)`. As a result:

- A transfer's `reference_id` must be unused on **both** the source and destination accounts, including by ordinary credits and debits on those accounts.
- Resubmitting the same transfer returns `409` and changes nothing; simultaneous duplicates are processed once.
- The same `reference_id` may be used for a transfer between two other accounts. Transfer references are not globally unique.
- If a request is both a duplicate and an overdraft, the duplicate error is returned.

### Atomicity and rollback

Everything happens in one database transaction:

1. Check both accounts exist (`404`).
2. Insert the transfer record and both ledger entries. A reused reference fails here, before any balance changes.
3. Debit the source with a conditional `UPDATE ... WHERE balance >= :amount` (`409 Insufficient balance` if no row matches).
4. Credit the destination with a conditional `UPDATE ... WHERE balance <= :maximum - :amount` (`409` if no row matches).
5. Commit.

If any step fails, including a database error after the source has been debited, the entire transaction is rolled back: both balances keep their previous values and none of the three records remain. A partial transfer cannot be committed.

## Error Reference

| Status | Meaning in this API | Returned by |
| ------ | ------------------- | ----------- |
| `200 OK` | Successful read | `GET` endpoints |
| `201 Created` | Resource created | `POST /api/accounts`, `POST /api/accounts/{account_id}/transactions`, `POST /api/transfers` |
| `404 Not Found` | Referenced account does not exist (`"Account not found"`, `"Source account not found"`, `"Destination account not found"`). Also returned by the framework as `{"detail": "Not Found"}` for unknown URLs. | All `/api/accounts/{account_id}...` endpoints, `POST /api/transfers` |
| `405 Method Not Allowed` | Framework response `{"detail": "Method Not Allowed"}` for an unsupported method on an existing path, such as `DELETE /api/accounts/1/transactions` | Any existing path |
| `409 Conflict` | Business rule violated: duplicate `reference_id`, insufficient balance, or balance limit exceeded | `POST /api/accounts/{account_id}/transactions`, `POST /api/transfers` |
| `422 Unprocessable Entity` | Invalid path parameter, query parameter, or request body | All endpoints except `GET /health` and `GET /api/accounts` |
| `500 Internal Server Error` | Unexpected failure. Database errors return `{"detail": "Internal server error"}`; details are logged on the server and never sent to the client. | Any endpoint that uses the database |

Database errors include SQLite lock timeouts: a write that waits more than 5 seconds for another write to finish fails with `500` and is fully rolled back. Any other unexpected (non-database) exception returns the framework's default plain-text `Internal Server Error` response, without a stack trace.

## Immutability

Supported transaction operations:

| Operation | Endpoint |
| --------- | -------- |
| Create a credit or debit | `POST /api/accounts/{account_id}/transactions` |
| Create a transfer (two linked entries) | `POST /api/transfers` |
| Read transactions | `GET /api/accounts/{account_id}/transactions` |

There are no endpoints to update or delete transactions, transfers, or accounts, and no endpoint to fetch or change a single transaction by ID. Once created, a transaction's type, amount, description, reference ID, account ID, and timestamp cannot be changed through the API. Requests such as `PUT`, `PATCH`, or `DELETE` on `/api/accounts/{account_id}/transactions` return `405`, and on paths that do not exist (such as `/api/accounts/{account_id}/transactions/{id}`) return `404`.

This immutability is enforced by the API. The database does not independently prevent direct SQL `UPDATE` or `DELETE` statements on ledger rows. Its foreign keys use `ON DELETE RESTRICT`, which only prevents deleting an account (or transfer) that ledger entries still reference.

## End-to-End Example

This walkthrough uses `curl` against a running local server. Account IDs are generated by the server, so the example stores them in shell variables; the responses show the IDs and timestamps you would see on an empty database, which will differ on yours.

**1. Create two accounts**

```bash
curl -X POST http://127.0.0.1:8000/api/accounts \
  -H "Content-Type: application/json" -d '{"name": "Alice"}'
```

```json
{"id": 1, "name": "Alice", "balance": "0.00", "created_at": "2026-10-27T12:00:00Z"}
```

```bash
curl -X POST http://127.0.0.1:8000/api/accounts \
  -H "Content-Type: application/json" -d '{"name": "Bob"}'
```

```json
{"id": 2, "name": "Bob", "balance": "0.00", "created_at": "2026-10-27T12:00:30Z"}
```

Store the returned IDs:

```bash
ALICE_ID=1
BOB_ID=2
```

**2. Credit Alice ₹1,000.00**

```bash
curl -X POST "http://127.0.0.1:8000/api/accounts/$ALICE_ID/transactions" \
  -H "Content-Type: application/json" \
  -d '{"type": "credit", "amount": "1000.00", "reference_id": "DEP-001", "description": "Salary"}'
```

```json
{"id": 1, "account_id": 1, "type": "credit", "amount": "1000.00", "description": "Salary", "reference_id": "DEP-001", "created_at": "2026-10-27T12:01:00Z", "balance_after": "1000.00"}
```

**3. Debit Alice ₹250.00**

```bash
curl -X POST "http://127.0.0.1:8000/api/accounts/$ALICE_ID/transactions" \
  -H "Content-Type: application/json" \
  -d '{"type": "debit", "amount": "250.00", "reference_id": "PAY-001", "description": "Groceries"}'
```

```json
{"id": 2, "account_id": 1, "type": "debit", "amount": "250.00", "description": "Groceries", "reference_id": "PAY-001", "created_at": "2026-10-27T12:02:00Z", "balance_after": "750.00"}
```

**4. Check Alice's balance**

```bash
curl "http://127.0.0.1:8000/api/accounts/$ALICE_ID/balance"
```

```json
{"account_id": 1, "balance": "750.00", "currency": "INR"}
```

**5. Transfer ₹300.00 from Alice to Bob**

```bash
curl -X POST http://127.0.0.1:8000/api/transfers \
  -H "Content-Type: application/json" \
  -d "{\"source_account_id\": $ALICE_ID, \"destination_account_id\": $BOB_ID, \"amount\": \"300.00\", \"reference_id\": \"TRF-001\", \"description\": \"Rent share\"}"
```
