## Scope

### Required by the assessment and implemented

- Create an account (§1).
- Add credit and debit transactions with per-account unique reference IDs (§2).
- Get an account's balance (§3).
- Get transaction history with type filtering, pagination, and latest-first sorting (§4).
- Data integrity: transaction immutability, balance consistency, and atomicity (§5).
- Validation and error handling (§7, §8).
- Bonus: money transfer between accounts (§9).

### Implementation additions not required by the assessment

- `GET /api/accounts` (list all accounts) and `GET /api/accounts/{account_id}` (account details).
- `GET /health` (health check).
- A `currency` field (`"INR"`) in the balance response.
- A `balance_after` field in the credit/debit response and `source_balance_after` in the transfer response.

### Out of scope

Authentication and authorization, multiple currencies, updating or deleting any resource, database migrations, a frontend, and deployment. None of these is required by the assessment.

## Account Behavior

| Topic | Behavior |
| ----- | -------- |
| ID generation | Integer primary key generated by SQLite. IDs are positive and unique. |
| Name validation | Required JSON string. Leading and trailing whitespace (including Unicode whitespace) is removed; the result must be 1–100 characters. Longer names are rejected, not truncated. |
| Name uniqueness | Not required. Two accounts may have the same name. |
| Initial balance | Always `0.00`. The create request accepts only `name`; sending `balance` or any other field returns `422`. |
| Creation timestamp | Generated by the application in UTC when the account is inserted. |
| Changes after creation | None. There are no update or delete endpoints for accounts. |

## Monetary Representation

| Topic | Decision |
| ----- | -------- |
| Currency | Indian rupees (INR) only. The assessment does not specify a currency; a single implicit currency is assumed. |
| API requests | Amounts are JSON strings containing a decimal number, such as `"500.00"`. JSON numbers are rejected (`422`) because JSON parsers read them as binary floating-point values, which can silently change large or precise amounts. Booleans are also rejected. |
| API responses | Amounts are strings with exactly two decimal places, such as `"1234.50"`. |
| In Python | `decimal.Decimal`. Floats are never used for money. |
| Storage | Whole paise (1 rupee = 100 paise) in SQLite `INTEGER` columns. ₹250.50 is stored as `25050`. SQLite has no exact decimal type, and its `NUMERIC` affinity can store values as floating point, so integers avoid rounding errors. A custom SQLAlchemy column type (`Money` in `app/models/base.py`) converts in both directions. |
| Precision | At most two decimal places. `"10.001"` is rejected rather than rounded. Inputs whose extra digits are zeros (such as `"500.000"`) are accepted because their value is exactly representable. |
| Positive amounts | Transaction and transfer amounts must be greater than `0`, checked by the API and by database `CHECK` constraints. |
| Maximum amount | `92233720368547758.07`, the largest value that fits in a 64-bit SQLite integer as paise. This is a storage limit, not a business limit. Amounts above it are rejected (`422`), and a credit that would push a balance above it is rejected (`409`). |
| NaN and Infinity | Rejected (`422`). |
| Input format leniency | The decimal parser accepts surrounding whitespace and exponent notation (`"1e2"` is `100.00`). |

## Transaction Semantics

| Topic | Behavior |
| ----- | -------- |
| Credit | Increases the balance by `amount`. |
| Debit | Decreases the balance by `amount`. |
| Insufficient funds | A debit larger than the current balance returns `409 {"detail": "Insufficient balance"}`. No transaction is stored and the balance is unchanged. A debit of exactly the full balance is allowed and leaves `0.00`. |
| Reference ID | Required string, trimmed, 1–100 characters. Unique per account, enforced by the database constraint `UNIQUE (account_id, reference_id)`. The same reference may be used on different accounts. |
| Duplicate requests | A reference already used on the account returns `409` with `"A transaction with this reference_id already exists for this account"`. No transaction is created, the balance does not change, and the original transaction is not returned. When a request is both a duplicate and an overdraft, the duplicate error takes precedence. |
| Description | Optional. Trimmed, at most 255 characters. Omitted, `null`, or blank descriptions are stored and returned as `null`. The assessment lists `description` as a transaction field but does not require a value, so it is treated as optional. |
| Failed transactions | Any rejected or failed request (`404`, `409`, `422`, `500`) stores nothing and leaves the balance unchanged. A rejected request does not use up its reference ID. |
| Immutability | The API offers no way to update or delete a transaction. See [Known Limitations](#known-limitations) for what the database does not enforce. |

## Transfer Semantics

| Topic | Behavior |
| ----- | -------- |
| Accounts | Both `source_account_id` and `destination_account_id` must exist (`404` otherwise; the source is checked first). They must be JSON integers; strings such as `"1"` are rejected. |
| Self-transfers | Not allowed. Source equal to destination returns `422`; the database also has a `CHECK` constraint for this. |
| Amount | Same rules as credits and debits. |
| Insufficient funds | Source balance less than `amount` returns `409 {"detail": "Insufficient balance"}`; nothing changes. |
| Records | One transfer record, one `debit` transaction on the source, and one `credit` transaction on the destination, all with the same timestamp. Both transactions carry the transfer's amount, reference ID, and description, and reference the transfer through `transfer_id`. |
| Atomicity | The transfer record, both transactions, and both balance changes are written in a single database transaction. |
| Rollback | Any failure, including one after the source has already been debited, rolls back everything. Both balances keep their previous values and none of the three records remain. |
| Reference ID scope | The `transfers` table has no reference column. The reference is stored on both ledger entries and therefore falls under the per-account uniqueness rule: it must be unused on both the source and destination accounts, including by ordinary credits and debits. A repeated transfer returns `409` and is never processed twice. The same reference may be reused for a transfer between two other accounts, so transfer references are not globally unique. The assessment states no reference requirement for transfers. |

## Balance Consistency

The account balance is stored on the `accounts` row rather than recomputed from history. Consistency between the stored balance and the ledger is maintained as follows.

**Application logic** (`app/routers/transactions.py`, `app/routers/transfers.py`):

- Every balance change happens in the same database transaction as the insert of the ledger entry that causes it, so both are committed or neither is.
- The ledger entry is inserted first, so a duplicate reference fails before the balance is touched.
- The balance is changed by a single conditional statement (`UPDATE ... SET balance = balance - :amount WHERE id = :id AND balance >= :amount RETURNING balance`), so the sufficiency check and the change cannot be separated by another request.
- Any exception triggers an explicit rollback.

**Database constraints**:

- `CHECK (balance >= 0)` on accounts, as a final safeguard against negative balances.
- `CHECK (amount > 0)` on transactions and transfers.
- Integer storage checks on every monetary column, and `NOT NULL` on required columns.

The database does **not** enforce that an account's stored balance equals the sum of its credits minus its debits. That invariant is maintained by the application logic above, not by a database constraint or trigger.

**Automated tests** (`tests/`) check that:

- credits, debits, and transfers produce the expected balances and ledger rows;
- rejected requests (duplicates, insufficient funds, missing accounts, invalid input) leave balances and row counts unchanged;
- injected database failures at each step (ledger insert, balance update, commit, and between the two transfer balance updates) roll back all changes;
- concurrent requests cannot overdraw an account, duplicate references are processed exactly once, and opposing concurrent transfers conserve the total balance (see [Database and Concurrency](#database-and-concurrency) for the scope of these tests).

## Transaction History and Pagination

| Topic | Behavior |
| ----- | -------- |
| Filter | Optional `type` query parameter: `credit` or `debit`. Without it, both types are returned. Other values return `422`. |
| `page` | Default `1`; integer from `1` to `92233720368547758`. The upper bound keeps the SQL offset within SQLite's integer range. |
| `limit` | Default `10`; integer from `1` to `100`. |
| Metadata | `current_page`, `page_size`, `total_records`, `total_pages` (`ceil(total_records / page_size)`, `0` when nothing matches). |
| Ordering | Newest first by `created_at`, then by `id` (highest first) for equal timestamps, so page boundaries are stable. |
| Empty results | An account with no matching entries, or a page past the last page, returns `200` with `"data": []` and correct metadata. |
| Invalid values | `page` or `limit` that are not integers or are out of range return `422`. |
| Transfers | Transfer entries appear in both accounts' histories as ordinary credits and debits. |
| Implementation | Counting and paging happen in SQL (`COUNT(*)`, then `ORDER BY ... LIMIT ... OFFSET`), backed by an index on `(account_id, created_at, id)`. |

## Error-Handling Conventions

| Category | Status | Body | Examples |
| -------- | ------ | ---- | -------- |
| Invalid input | `422` | FastAPI's validation error list in `detail` | Missing field, wrong type, amount `<= 0`, invalid transaction type, invalid pagination parameter, malformed JSON, unknown field |
| Missing resource | `404` | `{"detail": "<message>"}` | Account, source account, or destination account not found |
| Business-rule conflict | `409` | `{"detail": "<message>"}` | Duplicate reference ID, insufficient balance, balance limit exceeded |
| Unexpected server error | `500` | `{"detail": "Internal server error"}` for database errors | Database failure, SQLite lock timeout |

Input is validated before business rules are evaluated, so an invalid request returns `422` even when the referenced account does not exist. `409 Conflict` was chosen for business-rule failures because the request is well-formed but conflicts with the current state of the account. Database errors are logged on the server with full details, and the client receives only the generic message; no SQL, driver messages, or stack traces are returned. A non-database exception returns the framework's default plain-text `Internal Server Error`.

## Database and Concurrency

### Technology and initialization

- SQLite, through Python's built-in `sqlite3` driver and SQLAlchemy 2.x. The default file is `data/ledger.db`; `DATABASE_URL` selects another. Only SQLite is supported: the schema uses SQLite-specific checks such as `typeof(balance) = 'integer'`.
- On startup, the application creates any missing tables (`Base.metadata.create_all`). Existing tables and data are left untouched.
- Foreign-key enforcement is enabled on every connection (`PRAGMA foreign_keys = ON`), which SQLite does not do by default.

### Constraints

| Table | Constraints |
| ----- | ----------- |
| `accounts` | Non-blank `name`; `balance >= 0`; `balance` stored as an integer |
| `transactions` | `amount > 0`; `amount` stored as an integer; non-blank `reference_id`; `type IN ('credit', 'debit')`; `UNIQUE (account_id, reference_id)`; foreign keys to `accounts` and (optionally) `transfers` with `ON DELETE RESTRICT`; index on `(account_id, created_at, id)` |
| `transfers` | `amount > 0`; `amount` stored as an integer; `source_account_id <> destination_account_id`; foreign keys to `accounts` with `ON DELETE RESTRICT` |

Defaults for `balance` and `created_at` are applied by the application, not by the database schema.

### Transaction boundaries

Each request uses one database session. Each write endpoint (create account, credit/debit, transfer) commits once at the end of a successful request. The credit/debit and transfer endpoints roll back explicitly on any error, and any session that ends without a commit is rolled back when it closes.

### Concurrency behavior

SQLite allows only one writer at a time. A second write waits for the first to commit and then evaluates its conditional `UPDATE` against the updated balance. Simultaneous debits therefore cannot overdraw an account, and simultaneous requests with the same reference ID produce one transaction. A write that waits longer than SQLite's default 5-second lock timeout fails with `500` and is rolled back.

**What was tested:** the concurrency tests send simultaneous requests from multiple threads in a single process (synchronized with a barrier), against one SQLite database file, each request using its own database session. They cover concurrent debits, concurrent duplicate references, concurrent transfers from one source, concurrent duplicate transfers, and opposing transfers between two accounts.

**What was not tested:** multiple server processes (for example several Uvicorn workers) or multiple machines sharing the database file, and sustained high contention.

## Explicit Assumptions

Decisions on points the assessment leaves open:

| Topic | Assumption |
| ----- | ---------- |
| Currency | Single currency, INR. Amounts have at most two decimal places (paise). |
| Amount format | Decimal strings in requests and responses; JSON numbers are rejected. |
| Reference ID case | Case-sensitive: `TXN-1` and `txn-1` are different references. Surrounding whitespace is ignored. |
| Duplicate requests | Rejected with `409`. The original transaction is not returned (no idempotent replay). |
| Rejected requests and references | A request that is rejected (for example for insufficient balance) does not reserve its reference ID. |
| Insufficient balance status | `409 Conflict`. |
| Description | Optional; blank is stored as `null`. |
| Pagination defaults | `page=1`, `limit=10`, maximum `limit=100`. A page past the end is an empty result, not an error. |
| Timestamps | Generated by the server in UTC, returned as ISO 8601 with a `Z` suffix. The two entries of a transfer share one timestamp. Equal timestamps are ordered by ID. |
| Authentication | Not implemented; all endpoints are public. |
| Transfer references | Stored on both ledger entries; must be unused on both accounts; not globally unique. |
| Transfer response | Returns the source's resulting balance only; the destination balance is available from its balance endpoint. |

## Known Limitations

- **No migrations.** Tables are created with `create_all()` on startup, which does not alter existing tables. A schema change would require a migration tool such as Alembic or recreating the database file.
- **No authentication or authorization.** Any client can read or modify any account.
- **Immutability is enforced by the API only.** The database has no trigger or permission preventing direct SQL `UPDATE` or `DELETE` on ledger rows; foreign keys only prevent deleting accounts or transfers that ledger entries reference.
- **Balance-ledger invariant is not enforced by the database.** See [Balance Consistency](#balance-consistency).
- **Account list is not paginated.** `GET /api/accounts` returns every account.
- **No transfer retrieval endpoint.** Transfers are returned when created and appear in both accounts' transaction histories, but there is no endpoint to fetch a transfer by ID or reference, and `transfer_id` is not included in transaction responses.
- **Offset pagination.** If new transactions are recorded while a client is paging through history, entries can shift between pages.
- **SQLite write concurrency.** Writes are serialized. Under heavy contention, requests that wait more than 5 seconds fail with `500`. Multi-process deployments were not tested.
